--- title: "Building Reliable Kafka Consumers: Backpressure, Idempotency, Retries, and Failure Recovery" description: "A practical guide to building resilient event-driven systems with Apache Kafka, covering consumer lag, backpressure, circuit breakers, idempotent processing, transactional outbox, and delivery guarantees." tags: [kafka, distributed-systems, reliability, idempotency, microservices, architecture] --- # Building Reliable Kafka Consumers: Backpressure, Idempotency, Retries, and Failure Recovery Apache Kafka makes it possible to build scalable, event-driven systems. However, running Kafka in production introduces challenges that go far beyond publishing and consuming messages. What happens when consumers cannot keep up with incoming events? What if a downstream API becomes unavailable? What happens when a consumer updates PostgreSQL successfully but crashes before committing its Kafka offset? These are not exceptional situations. They are normal failure scenarios in distributed systems. Building reliable consumers requires more than increasing the number of partitions or adding retries. It requires controlling the flow of work, protecting downstream dependencies, handling duplicate deliveries, and designing explicit recovery mechanisms. In this article, we'll explore the patterns and trade-offs involved in building reliable Kafka-based systems. ## 1. Understanding Consumer Lag Consumer lag represents the difference between the latest available offset and the offset a consumer group has processed or committed. When producers publish events faster than consumers can process them, lag grows. ```mermaid flowchart LR P[Producers] --> K[Kafka] K --> C[Consumers] C --> D[(PostgreSQL)] C --> A[Third-party API] style K fill:#dcecff,stroke:#3973ac,color:#172b4d style D fill:#dff4e4,stroke:#42855b,color:#183d25 style A fill:#fff0d5,stroke:#c28b27,color:#49330d ``` Consider the following example: - Producers publish 10,000 events per second. - Consumers can process 8,000 events per second. - The difference accumulates as lag. Increasing the number of consumers might help, but only if the downstream dependencies have enough capacity to handle the additional load. If PostgreSQL is already saturated or a third-party API is responding slowly, adding more consumers can increase contention, connection usage, and request failures. **The first step is to identify the bottleneck before changing the architecture.** Useful metrics include: - Consumer lag by consumer group and partition. - Event processing latency, including p50, p95, and p99. - Database query latency and connection pool saturation. - Downstream API latency, error rates, and rate-limit responses. - Consumer rebalance frequency and processing failures. - Incoming event rate compared with successful processing throughput. Consumer lag is a symptom, not a root cause. ## 2. Backpressure: Controlling the Flow of Work Backpressure is the mechanism by which a system prevents incoming work from overwhelming its processing capacity. A common mistake is to assume that backpressure simply means reducing the number of consumers. In practice, it can involve several complementary strategies. ### 2.1 Limit concurrency and in-flight messages A consumer can receive more messages than it can safely process at once. For example, allowing hundreds of concurrent operations against a database with a limited connection pool may increase contention and latency instead of improving throughput. A safer approach is to introduce explicit limits: - Maximum number of messages being processed concurrently. - Maximum number of outstanding downstream requests. - Bounded internal queues. - Controlled batch sizes. ```mermaid flowchart TD K[Kafka messages] --> Q[Bounded work queue] Q --> L[Concurrency limit] L --> D[(Database)] Q -. queue full .-> P[Pause consumption] P --> Q ``` A bounded queue prevents the consumer from accumulating unlimited work in memory. When the queue reaches its capacity, the consumer can stop accepting additional work temporarily. The important distinction is that **batch size, concurrency, and queue capacity control different things**. A batch of 20 messages could be processed sequentially or with 20 concurrent operations. Those choices have very different effects on downstream load. ### 2.2 Pause and resume Kafka partitions Kafka consumers support pausing and resuming partitions. This is useful when a consumer has enough pending work or when a downstream dependency is temporarily overloaded. However, pausing consumption must be implemented carefully. The application still needs to manage polling, heartbeats, and offset commits correctly. Long processing intervals without appropriate polling can trigger consumer group rebalances. Pausing is a flow-control mechanism, not a way to increase processing capacity. ### 2.3 Apply rate limiting Concurrency limits control how many operations can be active at once. Rate limiting controls how many operations can start within a given period. Suppose an external API allows a maximum of 500 requests per second. Even if the consumer can process 2,000 events per second, sending requests at that rate may trigger throttling. A token bucket or leaky bucket algorithm can regulate the request rate. Rate limits should account for the provider's quotas, shared usage across application instances, and any tenant-specific limits. ### 2.4 Use batching to improve throughput Batching can reduce the overhead of repeated database operations. Instead of inserting 100 events with 100 separate database round trips, the consumer might insert them using a single batch operation. This can improve throughput, but larger batches may increase processing latency, memory usage, and the amount of work affected by a failure. Batching should be tuned against both throughput and latency objectives. ## 3. Protecting Downstream Dependencies Kafka consumers frequently depend on databases, HTTP APIs, payment providers, and other microservices. When a dependency becomes slow or unavailable, the consumer needs to avoid amplifying the failure. ### 3.1 Circuit breaker A circuit breaker monitors failures and temporarily prevents calls to an unhealthy dependency. It commonly has three states: - **Closed:** requests flow normally. - **Open:** requests are rejected locally without calling the dependency. - **Half-open:** a limited number of requests test whether the dependency has recovered. ```mermaid stateDiagram-v2 [*] --> Closed Closed --> Open: Failure threshold reached Open --> HalfOpen: Recovery timeout HalfOpen --> Closed: Probe succeeds HalfOpen --> Open: Probe fails ``` For example, if an external API starts returning repeated `503 Service Unavailable` responses, the circuit breaker can open and prevent every Kafka consumer from continuing to send requests. But a circuit breaker does not decide what happens to the messages that cannot be processed. The application still needs a policy: - Pause consumption and leave events in Kafka. - Route eligible failures to a retry mechanism. - Persist work for later processing. - Send permanently invalid messages to a dead-letter topic. The right choice depends on whether the event can safely wait, whether ordering matters, and how much retry delay the business can tolerate. ### 3.2 Respect rate limits and timeouts A provider may return `429 Too Many Requests` and include a `Retry-After` header. When available, that information should inform the retry policy. Repeatedly retrying immediately can worsen throttling. Requests should also have explicit timeouts. Without them, slow calls can occupy threads, connections, and in-flight capacity indefinitely. ### 3.3 Exponential backoff and jitter Exponential backoff increases the delay between retry attempts. A common formula is: `delay = min(maxDelay, baseDelay × 2^attempt)` Jitter introduces randomness into the delay to avoid synchronized retry bursts. With full jitter: `delay = random(0, min(maxDelay, baseDelay × 2^attempt))` Imagine 1,000 consumers retrying an unavailable API. Without jitter, many of them may retry at nearly the same time. With jitter, retry attempts are spread across a time window. Backoff reduces retry frequency; jitter reduces synchronization. Retries should be bounded or governed by an explicit retry policy. They should distinguish transient failures from permanent errors, and they must not bypass idempotency safeguards. ## 4. Delivery Guarantees: At-Most-Once, At-Least-Once, and Exactly-Once Before implementing idempotency, it is important to understand the delivery guarantees. ### At-most-once A message is processed zero or one times. A failure can cause work to be lost. ### At-least-once A message is not intentionally discarded before successful processing, but it can be delivered or processed multiple times. ### Exactly-once The intended effect occurs once within a clearly defined scope. Kafka supports idempotent producers to prevent duplicates caused by producer retries. Kafka transactions can atomically coordinate consumed offsets and records produced to Kafka topics. However, these guarantees do not automatically extend to arbitrary PostgreSQL transactions, HTTP requests, or external payment providers. For most consumers that update an external database, **at-least-once delivery combined with idempotent processing is a practical reliability strategy**. The objective is not necessarily to prevent every duplicate delivery. It is to make duplicate deliveries safe. ## 5. Idempotency: Making Duplicate Processing Safe An operation is idempotent when repeating it produces the same intended result as performing it once. Formally: `f(f(x)) = f(x)` In a distributed system, duplicate delivery can occur for several reasons: - A consumer crashes after updating the database but before committing the Kafka offset. - A consumer group rebalance causes previously processed records to be delivered again. - A producer retries after an ambiguous network failure. - An operator replays historical events. - A retry mechanism republishes a message. The key principle is: **Idempotency must be enforced at the business-effect boundary, not merely at the message transport boundary.** ### 5.1 Use a stable event ID Every logical event should have a stable identifier, such as `event_id`. That identifier should remain the same across retries of the same logical event. Do not generate a new ID for every delivery attempt. Otherwise, duplicate deliveries will look like new events. A Kafka offset can identify a record within a particular topic partition, but a domain event ID is generally more useful when the same event may be republished or transported through different systems. ### 5.2 Use a database-enforced uniqueness constraint An application-level check such as "Have I processed this event already?" followed by an insert is not sufficient by itself. Two concurrent consumers could both check, observe that the event is absent, and proceed. The database should enforce uniqueness. For PostgreSQL: ```sql CREATE TABLE processed_events ( consumer_name TEXT NOT NULL, event_id UUID NOT NULL, processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW(), PRIMARY KEY (consumer_name, event_id) ); ``` Including the consumer name allows different logical consumers to process the same event independently. The consumer can claim the event using: ```sql INSERT INTO processed_events (consumer_name, event_id) VALUES ('order-projection', :event_id) ON CONFLICT DO NOTHING RETURNING event_id; ``` If the statement returns an ID, the event was newly claimed. If it returns no row, that consumer has already processed the event. The claim must be part of the same database transaction as the business update. ### 5.3 Make the idempotency record and business update atomic A safe processing flow looks like this: ```mermaid sequenceDiagram participant K as Kafka participant C as Consumer participant DB as PostgreSQL K->>C: Deliver event C->>DB: Begin transaction C->>DB: Insert idempotency key alt New event C->>DB: Apply business update C->>DB: Commit transaction else Duplicate event C->>DB: Skip business update C->>DB: Commit transaction end DB-->>C: Transaction committed C->>K: Commit offset ``` Consider the failure windows: **Failure before the database transaction commits** The transaction rolls back, including the idempotency record. The message can be retried and processed normally. **Failure after the database transaction commits but before the Kafka offset is committed** Kafka may deliver the message again. The unique constraint identifies the duplicate, and the consumer skips the business mutation. **Offset committed before the database transaction commits** This is dangerous. If the consumer crashes after committing the offset but before persisting the business update, the message may not be delivered again, and the business effect can be lost. Therefore, for a typical at-least-once consumer, commit the database transaction before committing the Kafka offset. For concurrent processing within a partition, offset commits must also respect processing completion order. A later message must not cause the committed offset to advance past an earlier message that is still unprocessed. ### 5.4 Idempotency is more than deduplication Not every business operation can be made safe simply by storing an event ID. For example, applying an event that sets an order's status to `SHIPPED` may be naturally idempotent if the transition is properly guarded. An operation that increments an account balance by 100 is not naturally idempotent. Repeating it changes the balance twice. The implementation must protect the actual business effect, using techniques such as: - Unique event IDs and transactional processing records. - Conditional state transitions. - Unique business constraints. - Idempotency keys supported by downstream APIs. - Domain-specific checks preventing duplicate reservations, payments, or shipments. For financial operations, a stable idempotency key should identify the logical payment operation, not the HTTP request attempt. ## 6. The Transactional Outbox Pattern Idempotent consumers address duplicate processing, but another failure can occur before an event reaches Kafka. Imagine an Orders service that updates PostgreSQL and then publishes `OrderCreated` to Kafka. If the database commit succeeds but publishing fails, the order exists, but downstream services never receive the event. Reversing the order is not safe either: the event could be published while the database transaction later fails. The Transactional Outbox pattern solves this dual-write problem. ### 6.1 Write the business change and event together Within one PostgreSQL transaction, the service: 1. Persists the business change. 2. Inserts the corresponding event into an outbox table. 3. Commits the transaction. A separate publisher or CDC process subsequently publishes the outbox events to Kafka. ```mermaid flowchart TD C[Business command] --> T[PostgreSQL transaction] T --> B[Update business tables] T --> O[Insert outbox event] B --> COMMIT[Commit transaction] O --> COMMIT COMMIT --> PUB[Outbox publisher or CDC] PUB --> K[Kafka] K --> CON[Consumer] CON --> IDEM[Idempotent processing] ``` The business update and outbox event are committed atomically. If the transaction fails, neither becomes visible as a committed change. If it succeeds, the event remains available for publication. ### 6.2 The outbox publisher can still publish duplicates Suppose the publisher sends an event to Kafka successfully but crashes before marking the outbox record as published. After restarting, it may publish the same event again. That is expected in an at-least-once publication strategy. The outbox should assign a stable event ID, and downstream consumers should use that ID for idempotency. The Outbox pattern addresses reliable event publication. It does not eliminate the need for consumer-side duplicate protection. ## 7. Poison Messages, Retry Topics, and Dead-Letter Queues Not every failed event will succeed after another attempt. A temporary network error may recover quickly. A malformed payload, incompatible schema, or permanent business validation error may never succeed. Repeatedly retrying such a message can block progress or consume unnecessary resources. A robust strategy distinguishes between: - **Transient failures:** retry with backoff and jitter. - **Throttling:** respect provider limits and retry guidance. - **Permanent failures:** route to a dead-letter topic or another explicit terminal workflow. - **Ambiguous business outcomes:** reconcile the operation before retrying an irreversible action. Retry topics can help separate delayed retries from the main processing path. However, moving a failed message to a retry topic and continuing with later messages can change the effective ordering of events. If per-entity ordering is a business requirement, the retry architecture must preserve that requirement or explicitly define how out-of-order events are handled. Dead-letter handling should include observability, alerting, investigation procedures, and a safe replay mechanism. A dead-letter topic is not a substitute for deciding what a failed business operation means. ## 8. Scaling Consumers Without Overloading Dependencies Kafka consumers can scale horizontally, but scaling is constrained by partition count and downstream capacity. Adding more consumer instances can increase parallelism up to the number of partitions assigned to the group. Beyond that, extra instances may remain idle. Even before reaching that limit, the database or external API may become the bottleneck. A useful capacity model is: `Effective throughput ≤ min(Kafka capacity, consumer capacity, downstream capacity)` The exact relationship depends on batching, concurrency, partition distribution, and workload characteristics, but the principle is straightforward: the slowest constrained component limits the sustainable throughput of the complete pipeline. A practical scaling strategy should: 1. Measure processing throughput and latency. 2. Identify the saturated dependency. 3. Apply concurrency and rate limits where appropriate. 4. Optimize expensive database operations or external calls. 5. Increase partitions or consumer instances only when additional parallelism is useful. 6. Monitor lag and recovery time after traffic peaks. A growing lag is not always an immediate failure. If the system has enough retention and can process faster than the incoming rate after a peak, it may recover naturally. The critical question is whether the backlog is bounded and recoverable within the business's latency requirements. ## 9. Putting It All Together Consider an order-processing pipeline that consumes Kafka events, updates PostgreSQL, and calls an external API. A resilient design might combine: - Stable event IDs and idempotent database transactions. - Transactional Outbox for reliable publication from the source service. - Bounded concurrency and queues. - Rate limiting and circuit breakers for external dependencies. - Exponential backoff with jitter for transient failures. - Controlled offset commits. - Retry topics and dead-letter handling where appropriate. - Metrics for lag, processing latency, retries, duplicate suppression, and downstream health. These mechanisms solve different problems and should not be treated as interchangeable. | Pattern | Primary responsibility | |---|---| | Backpressure | Prevent overload by controlling the flow of work | | Rate limiting | Control the rate of operations | | Circuit breaker | Stop calls to an unhealthy dependency temporarily | | Exponential backoff + jitter | Reduce retry pressure and synchronized retry bursts | | Idempotent consumer | Make duplicate deliveries safe | | Transactional Outbox | Reliably persist business changes and events together | | Kafka transactions | Atomically coordinate supported Kafka operations | | Retry and dead-letter topics | Manage failures that cannot be processed immediately | The strongest design is not necessarily the one with the most patterns. It is the one that identifies the relevant failure modes and applies the smallest set of mechanisms that provide the required guarantees. ## 10. Final Thoughts Reliable event-driven systems are designed around the assumption that components can fail independently. Messages may be delivered more than once. Network timeouts may leave operations in an unknown state. Dependencies may become temporarily unavailable. Consumers may restart while processing. Backlogs may grow faster than they can be drained. A robust Kafka architecture makes those situations explicit rather than relying on the happy path. The most important principles are: 1. Measure before scaling. 2. Control the flow of work instead of allowing unbounded accumulation. 3. Protect downstream dependencies from overload. 4. Treat retries as a source of additional load. 5. Make business effects idempotent. 6. Commit offsets only when the corresponding work is safely complete. 7. Use transactional boundaries and the Outbox pattern to close dual-write gaps. 8. Define recovery, replay, ordering, and failure-handling policies explicitly. Kafka provides powerful primitives for building distributed systems, but reliability emerges from how those primitives interact with databases, APIs, and business logic. **The goal is not to prevent every failure. It is to make failures recoverable, duplicate delivery safe, and system behavior predictable under load.** --- ### Further Reading - [Apache Kafka: Message Delivery Semantics](https://kafka.apache.org/documentation/#semantics) - [Apache Kafka: Consumer Configuration](https://kafka.apache.org/documentation/#consumerconfigs) - [Apache Kafka: Producer Configuration](https://kafka.apache.org/documentation/#producerconfigs) - [AWS Prescriptive Guidance: Transactional Outbox Pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)
